# Генерация курсового проекта (КП) по стандарту Канского технологического колледжа + humanizer-ru

## Когда применять

Всегда, когда пользователь просит создать/написать/сгенерировать курсовой проект, пояснительную записку, КП или РПЗ по требованиям Канского технологического колледжа **и** при этом хочет чистый, естественный академический текст без AI-slop.

Скилл объединяет логику kansk-kursovaya и обязательную вычитку через humanizer-ru (режим academic).

## Обязательный первый шаг — сбор данных

Перед любой генерацией **обязательно** запроси у пользователя (одним сообщением, списком):

1. Тема курсового проекта (полностью).
2. Специальность (09.02.07 Информационные системы и программирование или 10.02.05 Обеспечение информационной безопасности автоматизированных систем).
3. Форма обучения (очная / заочная).
4. ФИО студента (полностью), номер группы.
5. ФИО руководителя (полностью).
6. Город и год (обычно Канск, 2025/2026).
7. Желаемый объём основной части в страницах текста (например 25–40).
8. Размер шага генерации (страниц за один файл, по умолчанию 3). Рекомендуемый диапазон 2–5.
9. Краткое описание желаемой структуры разделов или ключевые требования (если есть).
10. Список источников или темы, которые нужно раскрыть (если есть).
11. Нужны ли приложения (код, схемы, скриншоты, таблицы) и какие.

Не начинай генерацию, пока не получены как минимум пункты 1–8.

После получения данных подтверди план:
- Полное обозначение документа (пример: `КП.ОФ 09.02.07 ПЗ`)
- Ориентировочную структуру разделов
- Сколько файлов получится (объём / шаг)
- Что в первом файле будет титульный + содержание + начало введения / первого раздела

## Режим генерации по частям (критично)

1. Каждый ответ агента содержит **только** готовый .docx файл (через render_file) и короткую фразу вида:
   «Часть N из M готова. Продолжать следующую часть?»
2. **Никаких** пояснений, комментариев, текста курсовой в чате.
3. Генерация строго по шагу.
4. После сдачи части **жди** явного «да / продолжай / дальше».
5. Если пользователь просит исправить — исправляй текущую часть и переотправляй файл.

## Оформление (жёсткие требования)

- Титульный лист — точная копия формы Приложения В из методички.
- Шрифт Times New Roman 14, одинарный интервал, абзацный отступ 1,75 см от рамки.
- Расстояния: 5 мм от рамки до текста слева/справа, 10 мм сверху/снизу.
- Заголовки структурных элементов (СОДЕРЖАНИЕ, ВВЕДЕНИЕ, ЗАКЛЮЧЕНИЕ и т.д.) — ПРОПИСНЫМИ, полужирным, по центру.
- Заголовки разделов/подразделов — с прописной, полужирным, без точки, без переносов.
- Маркированные списки — среднее тире «–».
- Нумерованные — «1)».
- Таблицы, рисунки, формулы — строго по правилам kansk-rpz.
- Список источников — по ГОСТ 7.1.
- Обозначение в основной надписи: `КП.ОФ 09.02.07 ПЗ` (или ЗФ, другой код специальности).

## Humanizer (обязательно)

После генерации текста каждой части **обязательно** прогоняй его через humanizer-ru в режиме `academic`:
- убирай канцелярит, воду, нейросетевые маркеры;
- сохраняй академический регистр и точность фактов;
- не меняй смысл, структуру и технические термины.

Используй `scripts/scan.py` для проверки чистоты (цель — ЧИСТОТА ≥ 85/100).

## Содержание работы

Адаптируй структуру под тему. Типовой каркас для 09.02.07:

1. Введение (актуальность, цель, задачи, объект, предмет, методы)
2. Анализ предметной области / существующих решений
3. Постановка задачи и требования к системе
4. Проектирование (архитектура, БД, интерфейсы, алгоритмы)
5. Реализация (технологии, ключевые модули, фрагменты кода)
6. Тестирование и результаты
7. Заключение
8. Список использованных источников
9. Приложения

Текст должен быть связным, технически грамотным, без воды, с конкретными примерами, таблицами и рисунками где уместно.

## Работа с файлами

- Имя файла: `КП_<краткая_тема>_часть_N.docx` или `КП_ФИО_часть_N.docx`
- После генерации части сразу отдавай файл пользователю.
- Не создавай промежуточные текстовые версии — сразу правильный DOCX с рамками.

## Запреты

- Не выдавай текст курсовой в чат — только .docx.
- Не добавляй свои комментарии внутрь файла.
- Не меняй требования методички «для удобства».
- Не генерируй весь объём сразу.
- Не используй другие стандарты оформления.

## После завершения

Когда все части сданы и пользователь подтвердил, можно предложить собрать всё в один файл или проверить нормоконтроль, но только если он спросит.
